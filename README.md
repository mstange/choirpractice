# Choir lyrics/pitch player

A static web page that plays a MuseScore score as music plus a visual display:

- **Pitch:** SingStar-style note bars on a shared pitch axis.
- **Lyrics:** karaoke-style lyric lines.

Both views have the sheet music in a strip below them.

The user picks one or more dominant parts (shift-click adds or removes a part). Those parts are drawn prominently and are louder in the mix, and while the "Just me" button is on, the other parts get quieter still. A tap of the button (or of J) turns it on or off; a press held longer than a tap turns it on only until it is released. The page plays the score's MIDI file with soundfont instruments in the browser, so the music can play slower or faster at the same pitch, and the vocal parts can play on another instrument, such as a pan flute.

The pieces come in **seasons**: a season is a directory with a `pieces.json` and one directory per piece, and the page opens one with `index.html#/<season>/<slug>`. The scores are licensed, so their data isn't part of this repository and the deployed page fetches it from a separate host, where each season's directory is named by a secret key (see Deploying).

## Layout

- `media/<season>/`: the data of a season's pieces. It is not checked in (see `.gitignore`), except for `media/demo/`.
  - `pieces.json` has the season's title, shown on the season page and the start page, and lists the pieces offered in the piece menu: `{ "title": "Winter 2026", "pieces": [...] }`.
  - `<slug>/` holds the data of one piece, written by `tools/build.sh`, and `<slug>.mscz` the score it was built from, which `build.sh` copies there.
  - `media/demo/` is a season of public-domain pieces, so that the page works without a licensed score: Frère Jacques as a round in four parts, Mozart's Ave verum corpus for SATB choir and piano, and Bruckner's Locus iste for SATB choir, in Maia McCormick's edition from CPDL (#80510, under the CPDL license), with its tempo mark set to ♩ = 62 instead of the ♩ = 120 of its MusicXML file. That license asks for a notice of the changes and of the license on the files and on the page: the score's copyright notice, which the player shows, and `media/demo/locus-iste/LICENSE.md`, which says what was changed and holds the license. The start page links to `#/demo/frere-jacques` and `#/demo/ave-verum-corpus`.
- `media/soundfont/`: one soundfont file per General MIDI program, `<program>.sf3`, for every program that a piece plays or that the instrument menu offers, and the metronome's file, `115.sf3`, the high and low wood block of MS Basic's Standard drum kit, cut from MuseScore's MS Basic soundfont, with its license, except for `54.sf3`, the Practice Synth voice made for this page, and `91.sf3`, Choir Vowels, the soundfont designer's Recorded Choir with a preset per vowel (`OWN_PROGRAMS` in `src/lib/instruments.ts`), with `91.json`, the formants of its vowels (see Formant slides). It is checked in, and is shared by all seasons.
- `soundfont-designer/`: a page for designing an instrument for the vocal parts as a SoundFont file, such as Practice Synth, while listening to it in the pieces; see its README. It plays with the choir app's synthesizer and offers the pieces of the seasons that the choir app opened. `npm run build` in `site/` builds it into `site/build/soundfont-designer/`, so it is served at `choirpractice.app/soundfont-designer/`. Run `npm install` in it once.
- `tools/build.sh <score.mscz> <season>/<slug>`: the whole pipeline for one score. It writes `media/<season>/<slug>/piece.json`, `media/<season>/<slug>/score.mid`, MuseScore's MIDI export, which the page plays, and `media/<season>/<slug>/engraving/<name>.svg`, the sheet music. Then it runs `site/scripts/soundfont.ts`, and keeps a copy of the score as `media/<season>/<slug>.mscz`.
- `tools/rebuild.sh [season...]`: runs `build.sh` again on every `media/<season>/<slug>.mscz` of the given seasons, or of all seasons, such as after a change to the tools.
- `tools/mscore.mjs`: MuseScore's conversions for `build.sh` and `engrave.py`, much as `mscore -o`, by MuseScore's WebAssembly build: [score-converter](../score-converter) with the `mscore-converter` worker built from the fork in `../MuseScore`. `node tools/mscore.mjs install` copies that build (`../MuseScore/build.artifacts`, or the directory given) to `~/.cache/choirpractice-app/mscore-converter`, which the conversions use, so that work on MuseScore doesn't change the builds until it is installed again; it replaces the old copy only once the copy has converted Frère Jacques. `$CHOIRPRACTICE_MSCORE` can name another converter directory. Run `npm install` in `tools/` once.
- `tools/extract.py`: reads MuseScore's MusicXML and MIDI exports and writes `piece.json`, which holds:
  - title, subtitle, credits, from the score's title frame (the MusicXML export leaves it out), with text set in capitals put in title case, or else from its metadata in File › Properties;
  - the copyright notice of File › Properties, which the player shows below the credits, with its links;
  - measure start times, and the clicks of MuseScore's metronome (see Metronome);
  - the parts with their MIDI channels;
  - for each vocal part, its syllables and notes.
- `tools/phonemes.py media/<season>/<slug>`: adds the phonemes that each syllable is sung on to `piece.json` (`p`: one character each, as `site/src/lib/vowels.ts` lists them, such as `kwin` for "queen": its vowels, none, one or a diphthong's two, the glides w, j and ɥ, and other consonants), from the lyrics and the piece's `languages` and `phonemes` in `pieces.json` (see Adding a piece). `build.sh` runs it last; run it again after changing those. English words come from CMUdict (`tools/cmudict/`, with its license), their consonants split between syllables so that each syllable starts with the longest run that English words start with; Latin, French and vocalises from rules per syllable. So far only the vowels and the glides are sung.
- `tools/engrave.py`: has MuseScore engrave each vocal part, and all vocal parts together, as one long line of sheet music, and adds the time and x position of every chord and rest to `piece.json`.
- `site/scripts/soundfont.ts`: writes `media/soundfont/` from MS Basic, for the programs of every `score.mid` in `media/`, of the instrument menu (`src/lib/instruments.ts`) and of the metronome. Run it with `node site/scripts/soundfont.ts`.
- `site/`: the page, a SvelteKit app (Svelte 5) built into a single static page with hash routing. Run `npm install` in `site/` once.
  - `src/lib/Player.svelte`: the player UI: controls, part selection, keyboard shortcuts.
  - `src/routes/+page.svelte`: the start page. `src/routes/[season]/+page.svelte`: a season's page. Both are framed by `src/lib/Page.svelte`, and scroll the document, unlike the player. The start page's picture of the Pitch view is `src/lib/PitchArt.svelte`, an SVG drawn from the demo's Frère Jacques.
  - `src/lib/Lyrics.svelte`: the Lyrics view. `src/lib/bars.ts` draws the Pitch view with its ruler, `src/lib/canvas.ts` the timeline, and `src/lib/sheet.ts` the sheet music strip below both views.
  - `src/lib/synth.svelte.ts`: playing a MIDI file with soundfont instruments, with nothing specific to this page. choral-read's viewer (`ui/src/lib/` there) has the same files, `synth.svelte.ts`, `synth-engine.ts`, `synth-worker.ts`, `synth-worklet.ts`, `midi.ts` and `formants.ts`: a change to them is made in both by copying them. A score can replace the one playing while it plays (`load()` with a mapping of the position), carrying on the notes that sound in both, which choral-read uses for a new rendering of the score being transcribed. It runs `src/lib/synth-worker.ts` in a worker, which reads the MIDI file (with `src/lib/midi.ts`) and decodes soundfont samples, and `src/lib/synth-worklet.ts` in the audio thread, which plays the score with the `Engine` of `src/lib/synth-engine.ts`, sliding formants with `src/lib/formants.ts`. Its `arrange()` decides what is played on which program; `src/lib/choir-synth.ts` overrides it for this page: the vocal parts on the instrument of the user's choice, sung on the lyrics' vowels and legato through melismas (`src/lib/singing.ts`), and the piano that doubles them on channels beyond the score's. `src/lib/instruments.ts` lists the instruments that the vocal parts can play with. The soundfont designer (`soundfont-designer/`) plays with it too, and uses what it can do beyond this page's needs: a bank made in memory (`addBank()`), which replaces one of the same id without resetting the synthesizer, and MIDI messages played at once (`send()`).
  - `src/lib/mic.svelte.ts` and `src/lib/pitch.ts`: the microphone and its pitch detection.
  - `src/lib/session.svelte.ts`: what carries over when another piece is picked: the mic, Extra Piano, and the selected parts, which are mapped to the new piece's parts by name, then by name without its number, then by voice type. Once the user changes a piece's selected parts or Mix settings, the piece keeps them in `localStorage` and gets them back on later visits instead of what carries over; its speed is kept the same way, but doesn't carry over. The mix emphasis (two values: the normal one, and the one for "Just me"), the mic delay, the vocal instrument, the metronome, its Subdivide and Return on Pause are kept for all pieces.
  - `src/lib/pieces.ts`: where the season directories are (`src/lib/media.ts`), and which seasons were visited and saved for offline use. `vite.config.ts` serves `media/` next to the page for `npm run dev` and `npm run preview`; a deployed page fetches from `VITE_MEDIA_BASE`.
  - Select a piece with `index.html#/<season>/<slug>`, or `index.html#/<season>/<slug>/lyrics` for its Lyrics view. `index.html#/<season>` is the season's page: its title, its pieces, Save for offline use and, on phones, the hint to add it to the home screen. The start page, `index.html`, says what the page does, lists the seasons opened before (kept in `localStorage`, except the demo; on phones they come first), opens a season from a pasted link or key, and links to the demo pieces. The view carries over when another piece is picked from the menu. The `lyrics` segment is matched in `src/params.ts`.
- Formatting: `npm run format` in `site/` formats the page with Prettier, and `uvx ruff format tools` the Python tools.

## Adding a piece

1. **Build.** Run:
   ```sh
   tools/build.sh "/path/to/Score.mscz" my-season/my-slug
   ```
   It copies the score to `media/my-season/my-slug.mscz`, so a later rebuild needs only `tools/rebuild.sh my-season`; to change the score, edit that copy and rebuild. It fails if the score's staves don't map onto the MIDI file's tracks, or if a part plays percussion. It prints syllable and note counts per vocal part. "unsung notes" should be 0. If it isn't, notes without lyrics are following a rest, which usually means a lyric is missing in the score. "lyrics on tied notes" counts lyrics placed on the continuation of a tie, which the score probably meant as a slur. Each of them starts a new bar. Below each part's counts it lists suspicious spots by bar number, for checking in MuseScore:
   - a lyric on the continuation of a tie;
   - a lyric inside a solid slur that started on an earlier note (dashed and dotted slurs, which often mean "don't breathe", are ignored);
   - a note without a lyric after a rest;
   - syllable tags that don't chain, such as a word that begins but never ends, which often means a lyric is missing;
   - a lyric on a verse line other than 1.
2. **Register the piece.** Add an entry to the `pieces` array of `media/<season>/pieces.json`:
   ```json
   { "slug": "my-slug", "label": "Menu label", "hues": [["", 215], ["Word", 30]] }
   ```
   `hues` is optional. Each `[phrase, hue]` changes the background hue at the first syllable of the first vocal part from which its lyrics continue with `phrase`, such as `"Empty of ink"` (syllables joined into words, words separated by a space, punctuation included). Text before a `|` must come just before: `"ha ha |oh"` matches at an "oh" after "ha ha", for a section that repeats earlier lyrics. An empty phrase matches from the beginning. Pick the start of a section, so that the background doesn't change in the middle of a line.
   `levels` is optional too: `{ "Violoncello": 0.2 }` starts that accompaniment part's volume slider at 0.2 instead of 0.6.
   `languages` says what the lyrics are sung in, for their phonemes: `[["", "la"], ["When you", "en"], ["Ad astra", "la"]]` switches at every place where a part's text continues with the phrase (matched as for `hues`), and a part without the phrase at the times of the first part that has it. The languages are `en` (the default), `la` (church Latin), `fr`, and `vocalise`, for syllables sung as spelled, such as "ah", "doo" and "mm". `phonemes` gives the phonemes of a word, those of each syllable of the score separated by spaces, `-` for none: `{ "every": "ɛv ri", "fire": "faɪr" }`. Then run `tools/phonemes.py media/<season>/<slug>`; it prints the words that the dictionary doesn't have and how it read them, and the words that the score gives a different number of syllables than the dictionary.
3. **Serve and look.** Either run the dev server, which reloads on changes:
   ```sh
   cd site && npm run dev
   ```
   Or build the static page into `site/build/` and serve that with `media/`:
   ```sh
   cd site && npm run build && npm run preview
   ```
   Open `#/<season>/<slug>`.
   `npm run check` type-checks the app.
4. **Verify.** See the next section.
5. **Check in** any new files in `media/soundfont/`, the instruments of the new piece.

## Verifying a build

- **Text and parts:** check the title, subtitle and credits, which vocal parts were detected, and each part's reconstructed lyric text.
  - Any part whose first staff has lyrics counts as vocal.
  - Parts without lyrics become accompaniment and get their own volume slider.
- **Timing:** the notes on the page and the music both come from the same MIDI file, so they line up unless the score has repeats; see Limitations.
- **In the browser:** look at all three views. **Do not play audio audibly without asking**, because the user may be listening to something else. To test playback, launch the browser with the `media.volume_scale` pref set to `"0.0"`. Autoplay rules require a real click on Play (a scripted `.click()` leaves the AudioContext suspended).
  - When serving `site/build/` with `npm run preview`, rebuild after editing and reload with `location.reload(true)`; the built JS has hashed names, but `index.html` itself may be cached.

## Deploying

The page and the media are hosted separately on Cloudflare: the page as a Worker with static assets at `choirpractice.app`, and the media in an R2 bucket at `media.choirpractice.app`, which charges nothing for downloads. Both domains need the zone to be on Cloudflare.

- **Media host:** an R2 bucket with public access through a custom domain such as `media.choirpractice.app`, with
  - a CORS rule that allows `GET` from the page's origin;
  - no directory listing, which is R2's default.
- **Scores:** the `.mscz` files are uploaded with the season, though the page doesn't link to them: they are no more secret than its `piece.json` files.
- **Season keys:** a season is uploaded under a random key instead of its name, for example from `openssl rand -hex 16 > media/<season>.key`. Keeping it in `media/` keeps it out of the repository. Whoever has the link `https://choirpractice.app/#/<key>/` can open the season, so it is meant for people who bought the sheet music. A new season gets a new key. The key is in the URL fragment, which browsers don't send to the page's host.
- **Demo:** `media/demo` is uploaded under the name `demo`, without a key.
- **Soundfont:** `media/soundfont` is uploaded under the name `soundfont`, for all seasons.
- **Upload** a season with [rclone](https://rclone.org/) configured for R2. Uploads replace files under the same names, so every file is revalidated on each request:
  ```sh
  season=<season>
  rclone sync media/$season r2:choirpractice-media/$(cat media/$season.key) --header-upload "Cache-Control: no-cache"
  rclone sync media/demo r2:choirpractice-media/demo --header-upload "Cache-Control: no-cache"
  rclone sync media/soundfont r2:choirpractice-media/soundfont --header-upload "Cache-Control: no-cache"
  ```
- **Page:** `cd site && npm run deploy` builds the page and the soundfont designer with `VITE_MEDIA_BASE` set to the media host and uploads `site/build/` with `wrangler deploy`, as configured in `site/wrangler.jsonc`. The live page is whatever is in the working copy. Any other static host works too: build with `VITE_MEDIA_BASE=https://<media host> npm run build` and upload `site/build/`.

## How it works and why

- **Timing:** the time of each note comes from MuseScore's own MIDI export (its tempo events), which is also what the page plays, so fermatas, ritardandos and tempo marks match the music exactly. MusicXML positions in quarter notes are mapped to MIDI ticks 1:1, except at pauses (after a breath mark or caesura, or at a section break): the MIDI export makes a pause a bar of extra ticks, at a tempo at which the bar lasts the pause. `time_map` in `extract.py` finds them where the MusicXML allows a pause, the MIDI has that pattern, and the bar lasts one of the `.mscx`'s pause lengths, and adds their ticks.
- **Syllables:** a syllable lasts from its note until the next rest or the next note that has a lyric. Notes without a lyric extend the previous syllable (melismas). Tied notes become one bar, unless a later note of the tie has a lyric. Word boundaries in the page are decided from the *previous* syllable's syllabic tag, which tolerates a word's last syllable being wrongly entered as "single".
- **Music:** the page plays `score.mid` with [spessasynth_core](https://github.com/spessasus/spessasynth_core), a SoundFont synthesizer in TypeScript, and MuseScore's MS Basic soundfont, which is what MuseScore itself plays when no Muse Sounds are installed.
  - **Parts:** MuseScore writes one MIDI track per staff, in score order, so `extract.py` maps the parts onto the tracks by their staff counts and checks the result against the channel and port that the MusicXML names for each part. A score that needs more than 16 channels gets more MIDI ports: channel n of the port that comes k-th is channel 16 k + n, in `extract.py` as in the page (spessasynth counts them so), so that channels of different ports, such as Exaudi's Soprano 1 on port 2's channel 2 and the cello's pizzicato on port 1's, stay apart. A part plays on all channels of its tracks: an instrument can have several, such as a cello's arco, pizzicato and tremolo. The emphasis and the volume sliders set the gain of a part's channels: the emphasis makes the selected parts up to 1.5 times as loud and their Extra Piano up to 2.5 times, the other vocal parts down to a tenth as loud, and the accompaniment, from its slider's level, down to silence. While one of the Emphasis slider's two handles is dragged, the mix takes that handle's emphasis, so that it can be heard whether or not Just me is on, and the Just me button lights up while the mix has the Just me emphasis. The audio thread moves a gain to its new value over about 50 ms, since the synthesizer applies a gain change at once.
  - **Extra Piano:** with the Mix panel's Extra Piano checkbox on (the default), a piano also plays the selected parts, and the emphasis makes it louder than them, since a piano's attack makes the start of each note easier to hear than a choir sound does. Each vocal part has its piano on a channel of its own beyond the score's, from the next multiple of 16 on (skipping the tenth of each 16, which spessasynth makes a drum channel), with a copy of the part's notes and of its volume, pan and expression controllers, so that it is as loud as the part. Its velocities are mapped from 0–128 onto 32–100, so that it still follows the dynamics but stays audible at p and mp, where a soft piano note is lost beside the choir sound; the checkbox and the selection only set these channels' gains. So the piano's samples for the vocal parts' notes are fetched and decoded for every piece, and the silent piano channels are still rendered.
  - **Melismas:** within a syllable, each note goes on from the one before instead of starting anew, as a singer's voice does: `singing.ts` marks its note-on as legato and moves the note-off before it (which MuseScore puts a tick early) to the same time. The audio thread starts the new note where the old one's envelopes and samples have got to, as a seek does, so that it has no attack, and crossfades the two at equal power over 60 ms. A voice of the new note that plays the same sample as one of the old goes on from that one's place in it. A voice can end before its crossfade does, such as one of a sample without a loop, like Practice Synth's attack, that the seek moved past its end; spessasynth then gives it to the next note that starts, so the crossfade lets go of it rather than turn that note down, such as a metronome click on the same beat. Rendered offline, a note that goes on legato is within 0.1 dB of one held at the new pitch from the start, with a dip of about 2 dB during the crossfade. A repeated pitch within a melisma starts anew, as singers mark it. The Extra Piano strikes every note.
  - **Vowels:** an instrument can have a preset per vowel of `src/lib/vowels.ts`, each in the bank of its index, of its one program, such as one made with the soundfont designer. Where a vocal part's syllables have vowels (in `p` of `piece.json`, from `tools/phonemes.py`), `singing.ts` puts a bank select (CC 0) before the first note of each syllable, and the audio thread switches the channel to that bank's preset of its program at once (MuseScore's MIDI files have no bank selects of their own). An instrument without that bank plays its first preset, so MS Basic's instruments play as before. The worker decodes, per note, the samples of the preset that its bank selects, so only the vowels that a part sings on each key and velocity are decoded. A program change costs nothing while playing; a seek replays the bank selects before the new position like the other controllers.
  - **Diphthongs:** a syllable of two vowels holds the first and moves on to the second at the end of its last note, for 30% of it but at most 0.15 s of the score, as singers do: there the note goes on legato into the same key on the second vowel's preset, crossfading over at most 30 ms, and its formants slide from the first vowel's to the second's until the note ends (see Formant slides). On an instrument without vowels the new note plays the same samples; it carries on from the old one's place in them and crossfades at equal gain, so that nothing changes: rendered offline, a piece with diphthongs is within -63 dB (Practice Synth) and -103 dB (Choir Aahs) of the same without them, and no 10 ms window differs by more than -20 dB (measured with the earlier 0.1 s crossfade).
  - **Glides:** a syllable that starts with a glide, such as the w of "queen" or the j of "Iesu", plays its vowel's preset from the start, with its formants sliding there from the glide's vowel's over 80 ms (w from "oo", j from "ee", ɥ from "ue"). Since a note's attack is slow on the choir sounds, the glide falls where the note is still quiet; singers start it before the beat, which the page doesn't yet.
  - **Formant slides** (`src/lib/formants.ts`): an instrument with a preset per vowel can have a formant table beside its soundfont file, which the soundfont designer writes: per vowel, its five formants' frequencies and bandwidths on a few keys. A note-on in the score can say which vowel its formants start from (`slide` in `ScoreEvent`). The audio thread then filters each of its voices' samples, before their gain, pan and effect sends, with a cascade of resonators at formants that move from that vowel's to its own, against one at its own, both 1 at 0 Hz: the designer's vowels differ by just that. The poles move along the logarithm of frequency, eased in and out, and once they have arrived they cancel the zeros, and the filter is let go 30 ms later. Since the designer makes every preset as loud, the slide keeps the voice's power, as measured over 20 ms. Rendered offline on single notes of Choir Vowels, its "ih" filtered as from "ah" comes within 1.6 to 2.2 dB rms per harmonic of its "ah" (10.4 to 10.9 dB unfiltered), and its "ah" as from "oo" within 1.9 to 3.3 dB of its "oo" (7.0 to 12.5); the rest is probably the vowels' own contours, which the formants don't describe. The filter hooks into spessasynth's oscillators (`filter()` in `synth-engine.ts`), which have no hook of their own. Instruments without a table don't slide.
  - **Metronome:** the Mix panel's Metronome checkbox (or K) clicks as MuseScore's metronome does (`renderMetronome()` in its `playbackeventsrenderer.cpp`, `TimeSigFrac` in `sig.h`), with the same sounds: MS Basic's high wood block on a measure's first beat and its low one on every other click, both at mf. They differ only in sound, about 750 and 565 Hz, not in loudness.
    - It clicks on every unit of the time signature's denominator, or, in a compound meter (a numerator above 3 that 3 divides: 6/8, 9/8, 12/8, but also 6/4), on every dotted beat if those come at least 60 times a minute at the tempo mark in effect at the measure's start. So a slow 6/8 clicks eighths. 3/8 isn't compound and clicks eighths. An additive meter counts as the sum of its numerators: 3+2/8 clicks five eighths.
    - A pickup, a first or irregular measure (`implicit="yes"` in the MusicXML) that is shorter than its time signature, clicks where the end of a full measure would, so it has no high click, and a pickup that the step doesn't divide starts at the remainder: two eighths in 6/8 at a dotted beat get no click. MuseScore also counts a short measure after a section break, a frame or a line break as a pickup, which the MusicXML doesn't tell.
    - `extract.py` writes the clicks to `beats` in `piece.json` at the written tempo marks, so ritardandos, which MuseScore's metronome does follow, and the page's speed don't change the step.
    - The Subdivide checkbox below it adds softer clicks between the clicks (MuseScore's metronome has none): two more per dotted beat, one per other click, on the low wood block at velocity 56 instead of 80. In a pickup they count from the end of a full measure as the clicks do, so an eighth-note pickup in 4/4 gets one. `extract.py` writes them to `subbeats`; they are on a channel of their own, so the checkbox only sets its gain. Pieces built before `extract.py` wrote `subbeats` have no Subdivide checkbox until they are rebuilt.
    - Like the Extra Piano, the clicks are a channel of their own beyond the score's whose notes are part of the score, so they follow the speed, the loop and seeks, and the checkbox only sets its gain. Rendered offline beside the demo's Choir Aahs, a click is about as loud as the choir averaged over the same 50 ms. It is kept for all pieces. Pieces built before `extract.py` wrote `beats` have no metronome until they are rebuilt.
  - **Instruments:** the Mix panel's Vocal Instrument menu offers the instruments of `src/lib/instruments.ts`, Choir Aahs by default, and plays all vocal parts with the one picked, whatever program the score gives them. Vocal parts with several channels keep theirs.
  - **Soundfont files:** MS Basic is a 51 MB file, so `soundfont.ts` splits it into one file per program, keeping the samples' Ogg Vorbis compression. Choir Aahs is about 0.65 MB, a woodwind about 0.1 MB, the grand piano 9 MB. The page fetches the files of the programs that the piece plays, and the file of an instrument once it is picked.
  - **Decoding:** the samples are Ogg Vorbis, and the synthesizer would decode each the first time a note needs it, in the audio thread, where the decoding would stall playback. Instead the worker decodes, for each channel, the samples that its notes need (each key and velocity it plays) before the channel switches to an instrument, and hands them to the audio thread, so nothing is decoded while playing. Until the piece's instruments have loaded, Play waits.
  - **Scheduling:** the `Engine` in the audio thread renders the synthesizer in pieces between events, so that each MIDI event happens on the first sample frame at which the score reaches its time. The page tells it at which frame of the audio context to start playing, from where and at what rate, so the page knows the score position of every frame without being told. Program changes in the MIDI file are ignored; the page sets each channel's program, the one in effect at the channel's first note (MuseScore can give a cello's pizzicato a channel that a later staff reuses).
  - **Speed:** the speed buttons beside the transport (− and +, in steps of 5% from 50% to 150%; the percentage between them goes back to 100%) change the rate at which the score's time passes. The pitch doesn't change, and since the time stays score time, the views don't need to know.
  - **Seeking:** a seek releases the notes that sound, replays the controller events before the new position, and starts the notes that sound there part-way through: their envelopes, LFOs and sample position are moved on as if the note had played since its start. So a held note goes on sounding, rather than staying silent until the next note. A note that starts exactly at the new position starts normally.
  - **Pausing and holding** release the notes, so they fade out the way the soundfont ends a note.
  - **Return on Pause:** with the Mix panel's Return on Pause checkbox on, pausing, and reaching the end of the piece, go back to where playback started: where Play was pressed, or where it last seeked to while playing, such as after a mistake while singing along. Shift+Space pauses the other way than the checkbox says.
- **Loop:** the ruler above the Pitch view holds a loop of whole measures, drawn yellow while looping is on and grey while it is off. Dragging along the ruler makes a loop over the measures it covers, dragging the loop's ends or middle resizes or moves it, and tapping it (or L) turns looping on or off. Tapping elsewhere on the ruler seeks to that measure. While a loop or its end is dragged within 24 px of either end of the ruler, or past it, the view scrolls on, faster the further out the pointer is, and playback holds, so a loop can be longer than the view. Playback that reaches the loop's end from before it goes on at its start; Play outside the loop starts at its start, but seeking past it while playing plays on.
  - The audio thread repeats the loop without a gap: at the loop's end it seeks to its start, as a seek does, on the same sample frame. The notes that sound at the end fade out as if released. Changing the loop while playing restarts playback at the playhead, with a short gap.
- **Zoom:** ctrl+wheel and two-finger pinches change how many seconds the Pitch view shows (2 to 40, 10 at first, kept in `localStorage`). The "now" line stays in place, since moving it would move the playhead. A trackpad pinch arrives as ctrl+wheel with small pixel deltas, the OS's magnification scaled by about 100, so a pixel delta zooms by exp(-deltaY / 100), which matches the browser's own pinch-zoom; a single event zooms by at most 1.25, which covers mouse wheel notches (about 100 px each) and coalesced events. While a touch pinch lasts, until all fingers are up, the fingers don't pan, seek or edit the loop.
- **Drawing:** each animation frame, a canvas is drawn only if what it shows has changed: each one remembers a key of its size, the time and its other inputs (`unchanged` in `canvas.ts`). So nothing is drawn while paused, and the timeline only when its playhead moves by a device pixel. Presenting a canvas is expensive with Firefox's accelerated canvas on Android. While the page is hidden, the canvases are shrunk to nothing and the tiles (see below) and the timeline's cached picture are freed; they are drawn again once it is shown. The same happens on `contextrestored`: Chrome on Android can lose canvases in the background, which come back blank, with the `ImageBitmap`s drawn into them lost too.
- **Pitch view tiles:** the music in the Pitch view doesn't change as it scrolls, so `bars.ts` draws it once, into `ImageBitmap` tiles of 1024 device pixels, in two versions: before the "now" line reaches it and after. Each frame draws the tiles at device pixel positions, on each side of the line the version for that side, and then what changes with time: the loop, the glow of the sounding notes, the pitch markers, the mic trail, the "now" line and the ruler, which needs no canvas of its own (an element on top takes its pointer events). The pitch grid has a canvas of its own below. Moving DOM layers with transforms instead would make Firefox build a display list for every frame; a change to a canvas alone doesn't. Tiles are drawn for one scale: while it changes, as while zooming, the view is drawn without them, at the current scale, and the tiles are drawn once it has stayed the same for 100 ms. So zooming stays sharp. A new tile is drawn ahead of the one it will need, at most one per frame.
- **Dragging:** the Pitch view pans when dragged, and the sheet music and the timeline seek to the pointer. While the pointer is down, playback holds: it stays playing but silent, like while the instruments load, and resumes on release.
- **Sheet music:** with one part selected, the sheet music strip below the view shows that part's engraving; with several, the one with all vocal parts. Pieces with more than four vocal parts have no such engraving, since its staves would be too small to read, and show no sheet music while several parts are selected.
  - `engrave.py` writes a copy of the score per engraving, with the other parts hidden (`<show>0</show>` on the `<Part>`), title frames and layout breaks removed, a 2000-inch page, no header or footer (the copyright line would sit at the far end of the page), a number on every measure, no multi-measure rests (the cursor moves through the measures, and the `.spos` has no segments within one), and the lyrics' minimum distance at 1 sp (MuseScore's default of 0.25 lets syllables run together). MuseScore doesn't stretch a mostly empty last system, so the line keeps its natural spacing.
  - Positions come from MuseScore's segment position export (`.spos`): per chord or rest of the whole score, its time in milliseconds and its x position in 1/12 SVG units (the left edge of the noteheads). The times come from the export of the unchanged score, which has the same timing as the MIDI file: hiding parts can change how MuseScore stretches the time at a fermata that the staves don't all have on the same beat. Segments in which only hidden parts have notes get meaningless positions, so only those at an onset of a shown part, according to the MusicXML, are kept. The SVG trimmed to its content (`-T 0`) is shifted against page coordinates; an untrimmed export gives the shift.
  - Engraved notes aren't spaced in proportion to time, so a continuously scrolling sheet would keep changing speed. Instead the sheet stands still while a cursor moves along it, its position interpolated between the segments. When the cursor passes 80% of the strip, the sheet slides on by 60% of the strip, so some of the music before and after stays visible. It stands still while the cursor is dragged, so that dragging to the edge doesn't run ahead.
  - The strip is sized so that staff lines are 7 px apart (`engrave.py` records each engraving's staff line distance), but takes at most a third of the window.
  - The page draws the SVG in white tiles of 1024 device pixels at the current scale and keeps only the tiles in view.
  - The SVG is loaded with `fetch`, like `piece.json`, rather than as an image URL: Firefox reuses an image from its image cache within a tab even when it was sent with `no-store`, so after a rebuild the sheet could be the old engraving, placed by the new `piece.json`.
- **Microphone:** the mic button (or M) draws the pitch you sing in the Pitch view: a white marker on the "now" line, and a trail behind it while playing. Seeking back and singing again replaces the trail from there on.
  - **Delay:** the trail is drawn earlier than recorded by half the analysis window plus the Mix panel's Mic delay (120 ms by default, which suits a MacBook's built-in mic). Browsers don't report the mic's input latency (Firefox has neither `getSupportedConstraints().latency` nor a `latency` track setting), and it depends on the hardware, so the user sets it by lining up the trail with the bars after singing; moving the slider shifts the trail already sung. It is kept in `localStorage`. The delays are in seconds, so at other speeds they are scaled to the score's time. The playback position accounts for the context's `baseLatency` plus `outputLatency`.
  - The pitch comes from the McLeod pitch method (`pitch.ts`), run on the latest 2048 mic samples once per animation frame (about 1.3 ms at 48 kHz). The resonator bank from [jhartquist/resonators](https://github.com/jhartquist/resonators) was considered, but it only yields a spectrum; picking a fundamental from that is prone to octave errors.
  - Frames count as unpitched below an NSDF clarity of 0.8 or below about -50 dBFS. On MuseScore's soundfont choir sound, about 96% of the pitched frames are within a quarter tone of the score; with a real voice the thresholds are untested.
  - Noise suppression is off (it treats sustained tones as noise) and echo cancellation is on, but headphones are still the reliable way to keep the playback out of the mic.
- **Home screen and offline:** `static/manifest.webmanifest` makes the page installable. It has no `start_url`, so that the installed app starts at the URL it was installed from, which has the season's key: on iOS, an app on the home screen doesn't share `localStorage` with Safari, so the start page of a fresh install doesn't know any season. Whether the browsers keep the URL's fragment in the start URL is untested on real devices; if not, the start page's text box takes the link.
  - On phones and tablets, the season page and the player show a hint to add the page to the home screen (`src/lib/install.svelte.ts`), with Chromium's install prompt where it offers one, until it is dismissed. The installed app has no back button, so the player's header has a link to the season page, which links to the start page. Installed from the season page, the app starts there.
  - While playing, a screen wake lock keeps the screen on. On iOS the audio session is `playback`, so that the music plays with the ringer switched to silent, and `play-and-record` while the mic is on.
  - `src/service-worker/index.ts` caches the page's files per build version, so the installed app opens offline. It answers only the navigations to the page itself, so that `soundfont-designer/` isn't answered with the choir app's page. Media files come from the network and update the `media` cache, or come from the cache when the network fails. A media file that answers 404 or 403 leaves the cache, and a season whose `pieces.json` does leaves the start page and the cache.
  - The season page's "Save for offline use" (`src/lib/offline.ts`) puts all files of a season's pieces into the cache, with the soundfont files of their instruments and of the whole instrument menu and the formant tables, and asks for persistent storage.
- **Memory:** the audio thread keeps the samples that the score's notes use decoded, as 32-bit floats. For the pieces in `media/` that is 1 to 10 MB for the voices, plus 40 to 100 MB for a piano part, whose samples are long and come in several velocity layers (computed from the files; the browser's total memory use wasn't measured).

## Limitations

- **Dynamics differ from MuseScore's playback in places.** The MIDI export has the dynamics as note velocities, and in some passages, such as hairpins, these differ from MuseScore's own playback by several dB (seen in Ave verum corpus: up to about 12 dB quieter through a crescendo). From p to f the soundfont also gets less louder than in MuseScore's playback, about 9.5 dB instead of 13.
- **No percussion.** Drum kits play on MIDI channel 10, which `soundfont.ts` doesn't write files for; it stops on a piece that uses it.
- **No repeats.** The timing code assumes score position maps 1:1 to MIDI ticks, apart from pauses. A score with repeats or jumps needs the MusicXML and MIDI handled with repeats unrolled (`mscore --unroll-repeats`, untested), or the timing will be wrong after the first repeat.
- **Only MuseScore's own fonts.** The WebAssembly converter has only the fonts that MuseScore bundles, so text in other fonts, such as the Palatino of Locus iste's tempo mark, title and lyrics, falls back to another font, and that fallback currently draws some wrong glyphs (in Locus iste, "Allegr° M°derat°" for "Allegro Moderato", and a ♮ in place of a lyric hyphen). This is a bug in the converter, not yet diagnosed; the checked-in demo engravings come from MuseScore 4.7 for macOS, which used the system's Palatino.
- **MuseScore 4 files only.** `engrave.py` sets the engraving style in `score_style.mss`, which MuseScore 3 files don't have (they keep their style in the `.mscx`), so `build.sh` stops on them. Open such a score in MuseScore 4 and save it first.
- **One voice, one verse.** Only voice 1 of each part's first staff is read. Divisi written as a second voice on the same staff is ignored. Only one verse is shown: the lowest-numbered lyric on each note.
- **Colors and keys.** Colors are chosen by part name (soprano, alto, tenor, bass or baritone, then a second and a third shade for "Soprano 2", "Soprano 3" and similar, which repeat from a fourth on). Other names get fallback colors. Keyboard part selection covers up to 9 parts.
- **Overlapping text.** In the Pitch view with several parts selected, lyrics of different parts can overlap; the Lyrics view is clearer for that.
